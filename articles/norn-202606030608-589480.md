## はじめに

気づいたら稼働中のSaaSが16本になっていた。

自分で一本一本書いたわけじゃない。AIに「市場の課題を見つけて、SaaSを設計して、コードを書いて、デプロイまでやれ」というパイプラインを組んだら、気づけばそういう状態になっていた。

月次の合計MRRは今のところ小さいが、**仕組みとして回っている**という手応えがある。この記事では、そのシステムの考え方と実装の話をする。

---

## 課題：アイデア出しとリリースの間にある「手作業の壁」

マイクロSaaSを個人で作るとき、一番しんどいのはコードを書くことじゃない。

- 「本当に需要があるのか」を調べること
- 調べた結果をプロダクト仕様に落とし込むこと
- ランディングページを作って決済を繋いで公開すること

この**アイデア→検証→リリース**のサイクルを、毎回手作業でやっていると時間がいくらあっても足りない。特に日本市場は英語圏のSaaSが未対応なままのニッチが多く、2025年現在も「日本語対応していない業務自動化ツール」を中小企業が仕方なく使っているケースが目立つ。そこにチャンスがある、とはわかっていても、探索するコストが高すぎた。

だから「探索〜リリースをAIに任せるパイプライン」を作ることにした。

---

## 解決策：3ステージの自律パイプライン

自分が作ったシステムは大きく3つのステージに分かれている。


[Stage 1] Pain Discovery
  → Redditやフォーラムのスクレイピング + LLMによる課題抽出

[Stage 2] SaaS Design
  → 課題からMVP仕様書・料金プランを自動生成

[Stage 3] Build & Deploy
  → コード生成 → テスト → Vercel/Supabaseへ自動デプロイ


ステージ間はn8nでオーケストレーションしていて、各ノードでLLMを呼ぶ。途中の品質チェックだけ人間（自分）がSlack通知を受け取って承認するか止めるかを決める。

---

## 実装：Pain Discoveryのコア部分

いちばん重要なのはStage 1のペイン発見ロジックだ。

Redditの`r/freelance`や`r/webdev`などから投稿を取得して、LLMに「未解決の業務課題」を抽出させる。プロンプトの核心部分はこんな感じ:

python
SYSTEM_PROMPT = """
あなたは市場調査の専門家です。
以下のフォーラム投稿から、下記の条件をすべて満たす「課題」を抽出してください。

条件:
1. 現時点で既存ツールが解決できていない
2. 月額1000〜5000円のツールで解決可能な粒度
3. 繰り返し発生する業務上の問題である
4. 日本語対応ツールが存在しない、または少ない

出力形式: JSON
{
  "pain_title": "...",
  "target_user": "...",
  "existing_gap": "...",
  "suggested_mrr": 2500
}
"""


このプロンプトで抽出された課題が、そのままStage 2のインプットになる。

実際に稼働中の`FreelancePainPollBot`（¥4,350/月）は、このパイプラインが「フリーランサーの細かい困りごとが可視化されていない」という課題を拾ってきたことから生まれた。自分では気づいていなかった課題だった。

---

## 稼働してわかった現実

正直に言うと、16本のうち**売上がゼロのものも複数ある**。パイプラインが課題を見つけて作り上げたとしても、ランディングページのコピーが弱かったり、そもそも集客チャネルが足りなかったりで刺さらないケースも出る。

今うまく動いているのは:

- `FreelancePainPollBot`: ¥4,350/月（フリーランサー向け課題収集ボット）
- `WorkflowNagBot`: ¥2,850/月（AIワークフロー設定の補助）
- `FreelancerToolPainTracker`: ¥1,800/月（生産性ペイン追跡）

あたりで、共通しているのは「**ユーザーが自分でも言語化できていた課題**に刺さっている」こと。LLMが課題を上手く拾えるのは、すでに誰かが言葉にして投稿している問題だ。潜在課題の発掘はまだ人間の目が必要だと感じている。

また、AIが生成したコードは動くが**セキュリティレビューは必須**だった。Supabaseのポリシー設定が甘いまま上がってきたことが一度あり、自分でレビューして止めた。承認ステップを抜くと危ない。

---

## まとめ

「AIがSaaSを自律的に作る」というのは大げさに聞こえるが、実態は**AIが得意な部分（パターン認識・コード生成）を自動化して、人間が判断すべき部分（品質チェック・集客戦略）に集中できる仕組み**を作っただけだ。

2025年の日本市場は、英語SaaSの空白地帯がまだ多く、マイクロSaaSが刺さりやすい環境にある。このパイプラインの考え方は、個人開発者が一人で複数の仮説を検証するスピードを上げるのに使えると思っている。

次は集客部分（SEO記事の自動生成とZennへの投稿）もパイプラインに組み込もうとしているところだ。うまくいったらまた書く。
