## はじめに

16本のSaaSを同時に稼働させていると、「人間がボトルネックになる瞬間」が必ず来る。

FreelancePainPollBotが新しいペインポイントを収集する。WorkflowNagBotがワークフローの詰まりを検出する。AIHtmlDiffAlertがHTML差分を報告する。それぞれのシステムが毎日データを吐き出してくるのに、そのデータを見て「次に何を作るか」を決めるのは結局、自分だった。

この非効率さを解消するために作り始めたのが、**ノルン（Norn）**というシステムだ。名前は北欧神話の「運命を紡ぐ存在」から取っている。自分でも少し大げさだとは思っているが、やっていることはシンプルで地に足のついたものだ。

---

## 課題：16本のSaaSを人間1人で見続けることの限界

現在の月次MRRの内訳を見ると、FreelancePainPollBotが¥4,350でトップだ。これはフリーランサーの「細かい困りごと」を集約するボットで、毎日100件前後のデータが入ってくる。

問題は**データが増えるほど、人間の判断コストも増える**という当たり前の事実だった。

- どのペインポイントが「次のSaaSのネタ」になりうるか？
- WorkflowNagBotで検出されたワークフローの詰まりは、新機能で解決できるか？
- SoloTaxReceiptBotの離脱ポイントはLPの問題か、UXの問題か？

これらを毎朝Notionに手でまとめていたが、正直しんどかった。LP改善のためにPageSpeed Insightsを回して、CVRを計算して、次の仮説を立てて……というサイクルを16本分こなすのは、もはや「個人開発」の規模ではない。

---

## 解決の方向性：AIに「観察→判断→提案」をループさせる

ノルンの設計思想は3つのレイヤーに分けている。

1. **観察（Observe）** ― 各SaaSのログ・ユーザーフィードバック・収益データを収集
2. **判断（Evaluate）** ― 収集したデータをLLMで分析し、優先度スコアを付与
3. **提案（Propose）** ― 「次に何をすべきか」をSlackに通知 or GitHubのIssueとして起票

重要なのは「自律実行はさせない」という設計判断だ。AIに勝手にコードをデプロイさせたり、課金設定を変えさせたりはしない。**人間の最終承認を必ず挟む**。これはコントロールを失わないための意図的な制約で、個人開発者の規模ではこれで十分だと思っている。

## 実装：評価パイプラインの核心部分

ノルンの評価ロジックの中心は、各SaaSのデータを構造化してLLMに渡す部分だ。以下は簡略化したPythonの例：

python
import openai
import json

def evaluate_saas_health(saas_data: dict) -> dict:
    """
    各SaaSの状態を評価し、優先度スコアと推奨アクションを返す
    """
    prompt = f"""
    以下のSaaSデータを分析し、JSON形式で返してください。

    データ:
    - サービス名: {saas_data['name']}
    - 月次収益: {saas_data['mrr']}円
    - 直近7日の新規登録数: {saas_data['new_signups']}
    - 直近7日の解約数: {saas_data['churns']}
    - ユーザーフィードバック抜粋: {saas_data['feedback_sample']}

    出力形式:
    {{
      "health_score": 0-100の整数,
      "priority": "high/medium/low",
      "top_issue": "最も重要な課題を1文で",
      "suggested_action": "次に取るべきアクションを1文で"
    }}
    """
    
    response = openai.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        response_format={"type": "json_object"}
    )
    
    return json.loads(response.choices[0].message.content)


これを16本分バッチ処理して、スコアの低い順にSlackへ通知する。毎朝9時に走るCronジョブとして動かしている。

次に、ノルン自身が「どの観察指標を追うべきか」を更新する仕組みも実験中だ。

yaml
# norn_config.yaml - ノルンが自己更新する設定ファイルの一部
observation_weights:
  mrr_growth: 0.35        # 収益成長への重み
  churn_rate: 0.30        # 解約率への重み  
  feedback_sentiment: 0.20 # フィードバックの感情スコア
  signup_velocity: 0.15   # 新規登録の速度

# このweightはノルンが週次で見直しを「提案」し、
# 人間が承認したときだけ更新される
self_update_mode: "propose_only"  # "auto"にはしない


`self_update_mode: propose_only` というフラグが設計の肝で、AIが「こう変えたい」と言ってきても、Gitのプルリクエストとして起票されるだけで自動適用はされない。

## 現時点での正直な評価

稼働して3週間だが、いくつか分かってきたことがある。

**良かった点：**
- 毎朝の手動確認作業が30分→5分になった
- FreelancePainPollBotのフィードバックから「確定申告ネタ」の需要を自動検出し、SoloTaxReceiptBotの改善優先度を上げる判断ができた
- 「何となく気になっていたが後回しにしていた」課題が可視化された

**まだ課題な点：**
- LLMの評価が時々的外れで、スコアへの過信は禁物
- フィードバックデータのノイズ除去がまだ粗い
- 16本分のAPI呼び出しコストが月に数百円かかる（許容範囲ではあるが）

## まとめ：「自律進化」は小さく始めるのが正解

ノルンを作って一番感じたのは、**AIに任せる範囲と人間が握る範囲を最初に決めることの重要性**だ。

「AIが勝手に全部やってくれる」という設計は、個人開発のスケールではむしろリスクが高い。自分のサービスが意図しない方向に動いたとき、責任を取るのも修正するのも自分だからだ。

「観察はAI、判断は人間、でも判断材料の整理はAIに手伝わせる」という分業が、今の自分にはちょうどいい。ノルンはまだ発展途上だが、16本のSaaSを一人で回すための実用的な相棒になりつつある。
