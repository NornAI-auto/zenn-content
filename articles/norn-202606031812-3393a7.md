## はじめに

現在、個人開発でマイクロSaaSを16本稼働させています。合計MRRは数万円規模で、決して「爆益」ではないですが、仕組みを作ってから新しいSaaSを追加するコストが大幅に下がりました。

この記事では「どうやって1人で16本を並行稼働させているか」という技術的な仕組みを、できるだけ具体的に解説します。

---

## 課題：1本ごとに作っていたら死ぬ

マイクロSaaSを量産しようとして最初にぶつかる壁は「インフラと認証とStripe連携を毎回ゼロから作るのがしんどい」問題です。

最初の2〜3本はそれぞれ個別に実装していました。結果、こうなります：

- 認証：Supabase Auth をそれぞれのプロジェクトで設定
- 課金：Stripe Webhook ハンドラを毎回書く
- デプロイ：Vercel に個別プロジェクトとして登録
- ドメイン：1本ごとに取得・DNS設定

4本目あたりで「これは仕組みを作らないと詰む」と気づきました。

---

## 解決策：SaaSスターターを内製テンプレート化する

考え方はシンプルで、**新しいSaaSを追加するときに「ビジネスロジックだけ書けばいい」状態を作る**ことです。

具体的には以下をテンプレートとして固定化しました。

### 技術スタック（固定）

| レイヤー | 採用技術 |
|---|---|
| フロントエンド | Next.js (App Router) |
| 認証 | Supabase Auth |
| DB | Supabase (PostgreSQL) |
| 課金 | Stripe |
| デプロイ | Vercel |
| メール | Resend |

毎回同じスタックを使うことで、設定のコピペとわずかな変更だけで新しいSaaSを立ち上げられます。

---

## 実装：テンプレートリポジトリの構成

GitHub に `saas-base-template` というプライベートリポジトリを持っていて、新しいSaaSを作るときはこれを `Use this template` でコピーします。

### ディレクトリ構成（抜粋）


saas-base-template/
├── app/
│   ├── (auth)/          # ログイン・新規登録
│   ├── (dashboard)/     # ログイン後のUI
│   └── api/
│       ├── stripe/
│       │   └── webhook/ # Stripe Webhookハンドラ
│       └── ...
├── lib/
│   ├── supabase.ts      # Supabaseクライアント
│   ├── stripe.ts        # Stripeクライアント
│   └── plans.ts         # 料金プラン定義
├── components/
│   └── billing/         # 課金UI共通コンポーネント
└── .env.local.example   # 必要な環境変数一覧


新しいSaaSを作るときの手順はこれだけです：

bash
# 1. テンプレートからリポジトリ作成（GitHub UIでポチるだけ）

# 2. 環境変数を設定（Vercel Dashboard）
VERCEL_PROJECT_NAME=new-saas-name
NEXT_PUBLIC_SUPABASE_URL=...
SUPABASE_SERVICE_ROLE_KEY=...
STRIPE_SECRET_KEY=...
STRIPE_WEBHOOK_SECRET=...

# 3. Supabaseで新プロジェクト作成 → マイグレーション実行
npx supabase db push

# 4. あとはビジネスロジックを app/(dashboard) に書くだけ


Stripe Webhook の処理、サブスク状態の管理、プランごとの機能制限ロジックはすべてテンプレートに入っているので、触る必要がありません。

## 実際のプロダクト例と得た学び

現在稼働中の16本の中からいくつかを紹介します。

**FreelancePainPollBot（¥4,350/月）**
フリーランサーの「細かい困りごと」を集約・可視化するBotです。Slackやフォームで収集したペイン情報をダッシュボードで確認できます。ビジネスロジック自体はシンプルで、テンプレートからの差分コードは約400行程度です。

**WorkflowNagBot（¥2,850/月）**
MCPやn8n連携の設定をガイドするツールです。「設定が煩雑すぎて挫折する」というペインを拾っていて、チェックリスト形式で手順を管理できます。

**学び：小さく始めるほど継続できる**

最初は「機能が少なすぎて恥ずかしい」と思っていましたが、マイクロSaaSのユーザーが求めているのは「1つのペインを確実に解消すること」だけです。多機能にするより、解約ボタンを目立たせないことより、**そもそも解約したくなるほど価値を感じてもらうこと**の方が重要でした。

## 運用コスト

16本稼働させていても月の固定費はそれほど高くありません。

- Vercel Pro：$20/月（複数プロジェクト共有）
- Supabase：$25/月 × 必要プロジェクト数（無料枠で賄えるものも多い）
- Stripe：決済手数料のみ（月額固定費なし）
- ドメイン：1本あたり年$10〜15程度

全体で月$100〜150程度に収まっています。

## まとめ

マイクロSaaSを量産するポイントをまとめます。

1. **テンプレートを1本だけ丁寧に作る**：認証・課金・デプロイの共通処理を先に固める
2. **スタックを固定する**：毎回同じ技術を使うことで習熟度が上がり、トラブル対応も速くなる
3. **ビジネスロジックだけ変える**：新しいSaaSの差分が小さいほど、リリースまでの時間が短くなる
4. **小さく出して反応を見る**：最初から作り込まず、ペインが刺さるかどうかを先に確認する

「量産」と書くと聞こえが悪いかもしれませんが、実態は「同じ仕組みの上で、異なるペインを解決するプロダクトを並べている」だけです。テンプレートの品質を上げるほど、1本1本のSaaSの品質も上がる。この構造が気に入っています。
