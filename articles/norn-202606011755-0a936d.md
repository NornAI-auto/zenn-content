## はじめに

現在、個人で16本のSaaSを稼働させている。

合計の月次収益は細かくは書かないが、たとえば `FreelancePainPollBot` が¥4,350/月、`WorkflowNagBot` が¥2,850/月といった具合に、小さいものが積み重なっている状態だ。

これだけの本数を**一人で**維持できているのは、AIエージェントに仕事の大半を委任するアーキテクチャを組んでいるからに尽きる。今回はその設計思想と、実際に動いているコードの断片を紹介する。

---

## 問題：本数が増えると「管理コスト」が収益を食い始める

最初の3〜4本のうちは手動でも回せた。でも8本を超えたあたりから、以下のことが起き始めた。

- **ユーザーからの問い合わせ対応**に毎朝1〜2時間取られる
- **エラー検知が遅れ**、気づいたら数日落ちていたことがある
- **新機能のアイデア出し→実装→リリース**のサイクルが全SaaSで止まる

特に `AIHtmlDiffAlert` や `SoloTaxReceiptBot` のような、ユーザーが「設定でつまずく」系のツールは問い合わせが多い。自分が対応ボトルネックになっていた。

解決策はシンプルだった。**「自分がやっていたルーティン作業をエージェントのタスクとして定義し直す」**こと。

---

## 解決策：3層のエージェントアーキテクチャ

自分のシステムは大きく3層に分かれている。

### 1. モニタリング層（常時稼働）

SaaSのエラーログ・ユーザー行動ログを監視し、異常があれば次の層に通知する。ここはAIというよりルールベース寄り。

### 2. 判断・対応層（イベント駆動）

モニタリング層から通知を受け取り、**「これは自動対応できるか、人間が必要か」を判断する**エージェントが動く。LLMを使っているのはここが主。

### 3. 実行層（タスクキュー）

エージェントが生成した「やること」をキューに積んで、実際に処理する。メール送信・Slack通知・DBの自動修正など。

---

## 実装：問い合わせ自動トリアージの例

`SoloTaxReceiptBot` では「レシートのOCRが読めない」という問い合わせが頻出する。以下のコードは、問い合わせメール本文をLLMに渡して、自動返信できるカテゴリかどうかを判定するシンプルな例だ。

python
import openai
import json

def triage_support_email(email_body: str) -> dict:
    """
    問い合わせ内容を分類し、自動返信可能かどうかを判定する。
    """
    prompt = f"""
以下はSaaSユーザーからの問い合わせです。
次のJSONフォーマットで分類してください。

問い合わせ:
{email_body}

出力フォーマット:
{{
  "category": "ocr_error | billing | feature_request | other",
  "auto_reply_possible": true | false,
  "confidence": 0.0〜1.0,
  "suggested_reply": "自動返信する場合の文面（不可の場合はnull）"
}}

JSON以外は出力しないでください。
"""
    response = openai.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.1,
    )
    return json.loads(response.choices[0].message.content)

# 使用例
result = triage_support_email(
    "レシートを撮影してもエラーになります。iPhoneで撮った写真です。"
)
if result["auto_reply_possible"] and result["confidence"] > 0.8:
    send_auto_reply(result["suggested_reply"])
else:
    notify_human_required(result["category"])


これだけで、問い合わせの約60%は人間が見なくても返信が飛ぶようになった。残りの40%だけSlackに通知が来る。

## もう一つの実装：ペイン収集の自動集計

`FreelancePainPollBot` はフリーランサーが「困っていること」を投稿するツールだ。このデータを毎週LLMに要約させて、次にどのSaaSを作るか判断する素材にしている。

python
def weekly_pain_summary(pain_entries: list[str]) -> str:
    """
    1週間分のペイン投稿を要約し、未解決ニーズを抽出する。
    """
    joined = "\n".join([f"- {entry}" for entry in pain_entries])
    prompt = f"""
以下はフリーランサーが今週報告した困りごとです。

{joined}

以下の観点で日本語で要約してください：
1. 最も多く言及されたペイン（上位3つ）
2. 既存ツールで解決されていないと思われるニーズ
3. 次に作るべきマイクロSaaSの仮説（1〜2行）
"""
    response = openai.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
    )
    return response.choices[0].message.content


この要約が毎週月曜朝にSlackに届く。自分はそれを読んでGoかNo-Goを決めるだけだ。

---

## 正直に言うと、完全自律ではない

「自律収益」という言葉を使ったが、完全に放置して回っているわけではない。

- 週に2〜3時間は自分がログを見ている
- エージェントの判断が明らかに外れていることも月に数回ある
- LLMのAPIコストが増えたSaaSは採算を見直す必要がある

**「自分の判断が必要な仕事の総量を減らす」**のがゴールであって、ゼロにはなっていない。それでも、16本を一人で回せている実態はある。

---

## まとめ

- ルーティン作業を**「エージェントに渡せるタスク」として再定義**することが最初のステップ
- 完全自動化より**「人間の介入が必要なケースだけ通知が来る」設計**が現実的
- 問い合わせトリアージと定期サマリーの2つだけでも、管理コストは体感で半分以下になった
- SaaS本数を増やすより、**一本あたりの自動化率を上げる**ほうが先

小さくても動いているSaaSがあるなら、まずそのサポート対応をLLMに投げてみるところから始めると体感しやすい。コードは難しくない。判断の枠組みを設計するのが、結局一番時間がかかる部分だった。
